**1. What is Caching?**	

**Ans.** A cache is a temporary storage layer that keeps frequently accessed data closer to the application so that future requests can be served faster.

&#x09;

&#x09;User->Applications-> Cache(reading)--------HIT-----> Response

&#x09;			|--------MISS

&#x09;				  |

&#x09;				DATABASE

&#x09;				  |	

&#x09;			        CACHE(Updating)

&#x09;				  |

&#x09;				RESPONSE

&#x20;  It provides us faster access to the data that we expect to need again.



**2.Why do we need caching?**

**Ans.** If my application has n req/sec, and most are for the same product then without caching DB will be queried for n times. Which can be costly if n is too large. But with caching if the queries are mostly related to same product then the DB will be queried only for n-x times(x:- data that's retrieved from caching). Which will be a lot cheaper.

Gives us 3 major benefits:-

* Lower latency- Memory access is significantly faster than a db/network round trip.
* Reduced database load- DB doesn't need to repeatedly retrieve the same data.
* Higher throughput- Because many requests can be served directly from the cache, the system can handle much traffic.

**CACHE HIT:-** If the data exists in the cache then it's a cache hit.

**CACHE MISS:-** If the data isn't there then it's a cache miss.

**CACHE HIT RATIO:-**   cache hit/ total requests

**CACHE MISS RATIO:-**  cache miss/total requests

**STALE CACHE DATA:-** When the data is updated in the DB but the data in cache is still not updated hence returning the stale data.

**CACHE STAMPEDE/THUNDERING HERD:-**

&#x09;Suppose 10000 users requested for a same product- p1001 

&#x09;They got it from the cache.

&#x09;But now the key is expired.

&#x09;10000 requests are directly querying the DB can lead to DB overload and this is called thundering herd/Cache stampede

&#x09;**Prevention:-**

&#x09;	**1.Locking:-**

&#x09;		Allow only one request to fetch the missing data.

&#x09;		Request1->Cache Miss-> acquire lock-> DB

&#x09;		Request2->Cache Miss0-> Wait

&#x09;			.  	.	.

&#x09;			.	.	.

&#x09;		Once request1 gets the data we will be having 1 db requests and rest requests can be fulfilled by cache

&#x09;	**2.Randomized TTL/TTL Jitter:-**

&#x09;		Suppose 1M keys are having 10 mins of time and will expire together then to compromise that we can 

&#x09;		add like TTL = 10min + random(0-60 sec)

&#x09;	**3.Refresh before expiration:-**

&#x09;		For very popular data, you can refresh the cache proactively before it expires.

&#x09;		Cache almost expired--->Background refresh--->New Value

&#x09;				

&#x09;		Cache Entry - > Data in cache, TTL = 60s -> 50sec -> Refresh early -> Db-> Fresh Data-> Update cache-> TTL-> 60s

&#x09;		

&#x09;		No need to wait for a cache miss.

**HOT KEY:-**

&#x09;A single key becomes a hot key ( A single key is requested by large number of users at a same time).

&#x09;Preventions:-

&#x09;	replicating the hot value across multiple ache nodes.

&#x09;	Local caching at application servers

&#x09;	Request coalescing so identical concurrent requests share one fetch.

**Cache Penetration:-**

&#x09;Suppose users are requesting for a data that doesn't exist. So rather than having multiple cache miss we can save a NULL value in it so that we 

&#x09;wont be getting multiple DB hit.



**NOW COMES HOW THE DELETIONS OF CACHE WILL BE TAKING PLACE:-**

&#x09;**LRU - LEAST RECENTLY USED -** Removes the item that hasn't been accessed for the longest time.

&#x09;**LFU - LEAST FREQUENTLY USED -** Checks how many times an item has been accessed and removes the item with lowest frequency.

&#x09;**FIFO- FIRST IN FIRST OUT -** The oldest item is removed first

&#x09;**TTL - TIME TO LIVE -** Provides times for a cache to survive then will be deleted if it's time of expiration is crossed.





**WHAT SHOULD YOU CACHE?**

* High read frequency + relatively low change frequency
