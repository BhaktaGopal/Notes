**JWT - JSON Web Token**
Helps in _stateless_ authentication.
- A JWT has 3 Base64URL parts separated by dots:
  HEADER.PAYLOAD.SIGNATURE
**Refresh Token**
- Access token (JWT): Short TTL (e.g., 1-15 mins).
- Refresh token: Long-lived, stored securely. Used to get new access tokens.
Authentication vs. Authorization
- Authentication: Who are you? (Login/prove identity)
- Authorization: What can you do? (Permissions, roles)
Authentication
Stateful (Session-Based Authentication)
For each client, a session_id is generated by the server. For every request, the server has to verify the session_id that is stored in its cache.
Problems:
- If there is horizontal scaling, it is not possible that every server will have the data of every possible user.
- Even if we logically bind users to their specific server and that server goes down at any point, the users bound to that server will not be getting access.
To solve the stateful authentication issue, we needed JWT (can validate the user without checking the database).
JWT Structure
Part	Details
**Header**	-Algorithm + type (HS256 + JWT) in metadata.
**Payload**	-Information about the user, in JSON.
**Signature**-	Cryptographic signature: HMACSHA256(SECRET, base64url(header) + "." + base64(payload)).


Other notes:
- Secret/private key: Used to create the signature.
- JSON with HMAC (HS256).
Since the signature is encrypted, even if a man-in-the-middle attack is carried out on the payload and the data is changed, the data in the signature remains unharmed, so the profile service will.
The JWT signature provides integrity and authenticity. The server creates it using a signing key and the encoded header and payload. When a token arrives, the server verifies the signature to detect tampering and establish that the token was signed by a trusted key. However, the signature does not encrypt the payload or prevent token theft.
Private Key and Public Key
- Private key: Auth services - to create the signature.
- Public key: Other services - to verify the signature.
No sensitive information should be in the payload, and only necessary information should be there.
Where to Store JWT on the Client
- Web: Use HttpOnly, Secure cookies for access tokens, or use short-lived access tokens in memory + refresh token in an HttpOnly cookie. Protect against CSRF.
- Application: Keystore/Keychain.
**JWT and Authorization**
We cannot use a JWT token for authorization. For example, suppose we have a client A with role Admin, so accordingly it might have a JWT token. But now the role of client A is changed to Member. The JWT with the server might not be updated accordingly, so it might be storing the older token. Anyone can take advantage of this and can do some illegal stuff.
Refresh Token Types
- Opaque Refresh Token (mostly used).
- JWT Refresh Token.
Important Point
**JWT token is for integrity, not confidentiality. The server wants to know if the token is original or unchanged. For that, the signature is enough.**
